# Trail Gauge v2 implementation prompt

Continue the existing Trail Gauge app in the Hiking MVP workspace. Read the repository instructions, README, `dist/`, and `.openai/hosting.json`. The current app is a static site with a Leaflet basemap, hand-drawn route lines, weather presets, and browser-local profiles, groups, and reviews. Preserve the desktop and mobile layouts and the core flow: choose who’s hiking, compare routes, see the best fit for that group, and understand why. Treat the attached Submission 5 PDF as interview evidence and design reference. This prompt defines the work.

Build and verify in the following order. Complete each phase end to end before starting the next. If a provider lacks coverage, data rights, or required credentials, ship an honest unavailable state and document what’s needed to fill it.

## Phase 1 · Replace synthetic data

1. **Real routes.** Start with a verified subset in the existing parks. Use the [NPS public trail GIS layer](https://mapservices.nps.gov/arcgis/rest/services/NationalDatasets/NPS_Public_Trails_Geographic/FeatureServer/0) or official park GIS. Keep Leaflet if it serves the UI. Import licensed GeoJSON with a reproducible script or documented workflow. Store stable route IDs, source URLs, import dates, trailhead coordinates, geometry, park, and verified or clearly derived stats. Match each route to its park and trailhead. Confirm whether published mileage is one way, round trip, or loop, and align the displayed distance and time with that route. Render the same geometry on the region map and trail detail. Use sourced elevation data if available. Leave unverified routes or attributes unavailable. Retain attribution and check the [OpenStreetMap tile policy](https://operations.osmfoundation.org/policies/tiles/).
2. **Live forecasts and official conditions.** Use a real hourly forecast provider such as [Open-Meteo](https://open-meteo.com/en/docs), subject to [its terms](https://open-meteo.com/en/terms). Let the user pick a hike date and start time in the trail’s local time zone. Fetch temperature, apparent temperature, precipitation probability/type, and wind or gusts for the planned hike window. Sample the trailhead and a verified higher route point where appropriate. Show forecast times, source, last fetch time, and whether a cached forecast is stale. Feed relevant values into the existing estimate and explain their effect. Outside the forecast window or on failure, clearly mark weather unavailable and any resulting score as terrain/group only. Surface official park alerts and link to the park conditions page. The [NPS Data API](https://www.nps.gov/subjects/digital/nps-data-api.htm) can provide alerts if configured. Keep keys server-side. A forecast describes the weather and cannot confirm a route is open, a crossing is passable, or a surface is ice-free.
3. **Clean start and migration.** Remove seeded people, friends, groups, chats, history, ratings, review counts, crowds, weather presets, and the demo loader from the user-facing app. Use test fixtures only in tests. A new visitor starts with a profile setup and empty groups and history. Keep account-free local guests for organizers. Migrate existing user-created profiles, groups, reviews, and preferences while removing only records that can be reliably identified as seeded. Preserve old user data when provenance is ambiguous, and map old route IDs to the verified catalog when possible. Remove the sample thread and its entry point. Keep personal data browser-local for this release. Display real user-authored reviews as such, and hide aggregate ratings or popularity until a legitimate source is available.

## Phase 2 · Make the planning flow easier to use

4. **Discovery and navigation.** Make Explore the obvious start. Give users search by trail or park and filters for park, distance, and group fit. Add optional nearby discovery with browser permission and a manual park fallback. Let users save favorites, mark a trail as “Would skip,” and undo a hide. Simplify primary navigation and keep the active group easy to find.
5. **Compare and trail details.** Put mileage, elevation gain, estimated time, group difficulty, and the recommendation first. Use clearer headings, spacing, and row or column separators. Put less important details behind expansion. Rename score bars that show strain rather than fitness itself, using labels such as “Fitness demand for this group” and “Experience gap.” Include the real route map on the detail page, along with sourced surface, river crossings, and access notes when known. Add photos with verified reuse rights and credit. Keep the group-size and time-budget controls and explain when none of the selected trails fits.
6. **Packing and feedback.** Add a group packing checklist with progress and editable food, water, and gear entries. Explain suggestions using route duration, expected conditions, and user preferences. Make timed reminders optional because the interviews disagreed on their value. Avoid precise calorie or hydration prescriptions based on body measurements unless there is a validated method and a clear need. Extend real hike reviews with actual time, notes, surface or crossing observations, and optional cell-service observations with date and carrier. Label reception reports as user observations.

### Profile inputs and how to use them

- **Quick setup.** Keep it possible to plan with a nickname and rough fitness and experience. Ask for comfortable distance and elevation gain, or let the hiker enter one recent comparable hike with distance, ascent, elapsed and moving time where known, pack load, and perceived effort. Accept “I don’t know.” Existing profiles and local guests must work without filling in the new fields.
- **Advanced trail fit.** Ask optionally for recent hiking frequency, usual moving pace, comfort with steep descents, rough footing, exposure, and crossings, plus recent high-altitude experience and heat familiarity. Allow hikers to set firm limits and terrain they want to avoid. Capture estimated pack weight, planned breaks, and overnight stops as trip inputs. Skip required height, weight, age, sex, or medical history. Keep these planning fields private and separate from the public profile. Use grade in both directions and surface when available. Prefer recent comparable completed hikes over a self-rating for pace calibration and keep moving time separate from breaks. Start with a documented terrain-based baseline and label estimates as less certain when records or trail data are sparse. For groups, use the slower plausible pace and flag any member’s terrain or endurance limits. Show altitude considerations separately from physical effort and avoid inferring altitude safety from fitness. Explain which factors drove the result. [GPS-based hiking travel-time research](https://doi.org/10.1016/j.compenvurbsys.2022.101866) · [NPS group hiking guidance](https://www.nps.gov/articles/hiking-safety.htm) · [CDC altitude guidance](https://www.cdc.gov/yellow-book/hcp/environmental-hazards-risks/high-altitude-travel-and-altitude-illness.html)
- **Food.** Ask for dietary restrictions, allergens to avoid, foods the hiker likes and tolerates during exertion, usual intake on a similar hike if known, and whether they can cook. Use expected effort, time, days, and meal windows to propose editable snack portions and meals. Where label data exists, convert the plan into servings and show approximate carbohydrate totals. Treat sports-fueling ranges as optional guidance for sustained effort with a stated source and applicability. Keep during-hike snacks separate from overnight meals and reserve food. Avoid presenting calorie burn as a food requirement. Omit foods with unverified ingredients when an exclusion cannot be checked. [Joint sports nutrition position statement](https://pubmed.ncbi.nlm.nih.gov/26891166/)
- **Water.** Ask for typical water used on a similar hike or an optional already measured sweat-rate estimate, with the conditions it came from. Pair those inputs with expected duration, effort, heat, sun exposure if known, carry capacity, and time between confirmed usable refills. Show an editable planning range per person and a group total. Distinguish estimated use, starting carry, reserve, and refill assumptions. Treat sweat rate as context for the estimate and avoid treating it as a mandatory drinking rate. Label a generic estimate clearly when there is no comparable personal data. Avoid extrapolating personal intake across substantially different conditions without widening the estimate. Flag when a plan exceeds carry capacity or relies on an unverified refill. Treat untreated sources as requiring appropriate treatment and show any available park guidance. [NATA fluid replacement position statement](https://pmc.ncbi.nlm.nih.gov/articles/PMC5634236/) · [NPS trip planning guide](https://www.nps.gov/articles/upload/NPS-Trip-Planning-Guide-Package-1.pdf)
- **Learn from completed hikes.** Let hikers optionally log actual moving and elapsed time, pack weight, food eaten, water used and refilled, weather, and perceived effort. Show which comparable outings informed the next estimate. Keep defaults editable and let users remove a hike from calibration. Validate time ranges against held-out completed hikes before describing them as accurate. For food and water, compare suggested quantities with reported use and whether the user ran short, and keep those results separate from any claim about physiological needs.

## Phase 3 · Record hikes and share completed activities

7. **Record a hike.** Add Start, Pause, Resume, and Finish controls. Ask for location permission when the user starts recording. Show GPS status, elapsed time, moving time, distance, pace, and elevation gain when there are reliable altitude readings. Show the recorded path separately from the planned route. Filter inaccurate fixes and implausible jumps. Mark gaps when tracking is interrupted, exclude paused time from moving stats, and save drafts locally so a reload or temporary loss of connectivity doesn’t erase the hike. Explain the limits of browser recording when a phone locks or the browser is backgrounded. Use real location readings in the app and deterministic fixtures only in tests.
8. **Review and publish.** On Finish, save a private activity in History with the route and stats. Let the hiker add a title and notes, preview the shared view, and choose Private, Friends, or Community. Default to Private and require an explicit Publish action. Offer a summary-only post and a way to hide start and end sections before sharing a map. Share completed hikes only. Store only the selected public summary and trimmed path on the server when publishing. Keep the raw recording local and allow the owner to unpublish, change visibility, or delete the activity.
9. **Friends and community.** Add signed-in profiles and a shared backend for posts, friend requests, and visibility. Build Friends and Community feeds with recent activity cards, routes, and stats where the author shared them. Allow discovery by park or trail and let users send and accept friend requests from a community post. Keep discovery opt-in and based on chosen parks and shared posts. Show approximate park or trail locations in discovery results. Keep exact user location, local guest profiles, group membership, and private recordings out of discovery. Enforce post visibility and ownership on the server. Include blocking, reporting, and a way to handle reported posts before opening the community to the public. If the backend or account configuration is missing, report that dependency and verify against a local test backend with separate accounts.

## Phase 4 · Queue features that need field testing

Add backlog items with acceptance criteria for downloadable routes, offline basemaps from a provider that permits downloads, remaining time based on live pace, and estimates that learn from completed hikes. Treat GPX export and offline basemaps as separate capabilities. Field test recording under intermittent GPS and on locked phones before promising reliable background recording.

## Verification and handoff

Run the app locally and verify the full flow on phone and desktop. Check two routes against their sources, including one with distinct trailhead and upper-route weather. Test permission denied, missing geometry or photos, forecast failure, stale forecast, outside the forecast window, and a park alert. Verify a fresh browser contains no seeded personal content, a saved local guest can affect group fit, a real review survives refresh, and migration preserves user-authored data. Verify all provider attribution and that no secrets enter the client bundle. Document coverage, data sources, refresh cadence, setup steps, and what remains in the backlog. Finish with a reviewable preview and test results before proposing a production publish.

For activity tracking, test permission denied, pause and resume, missing altitude, poor GPS accuracy, reload recovery, and a recording gap. Use at least two separate accounts or browser sessions to verify sharing, friend request acceptance, visibility enforcement on direct URLs and API reads, and unpublishing. Verify that trimmed points and raw tracks are absent from shared payloads and that local guests never appear in discovery.

For personalization, test quick setup with missing values, an existing local guest, a slower hiker or a firm terrain limit, a longer or hotter hike with no confirmed refills, a carry-capacity shortfall, a dietary exclusion, and a relevant completed hike updating the next estimate. Confirm that private profile and nutrition details are absent from community payloads.
